Free Automation Strategy

How Trackly Will Automate Everything Without Paying for Servers

Trackly's Version 1 hosting is a static site on GitHub Pages — no server, no database, no paid infrastructure. This page is the complete, technically honest plan for how monitoring can still run on free-tier schedulers within those constraints, and where those constraints eventually stop being enough. It builds on the general pipeline described on the Automation Architecture page.

Change Detection Flow

From official page to notification queue

  1. Official Page — the institute's real, official page.
  2. Download — fetches the current page or file. Part of the future automation engine.
  3. Compare — checks it against the last known version. Part of the future automation engine.
  4. Verify — confirms the change is real and official. Part of the future automation engine.
  5. Queue — holds the verified update, ready to send. Part of the future automation engine.
  6. Future Notification — not built yet, the eventual last step.

Handling Edge Cases

What should happen when...

New PDF appears

Treated as a genuine update candidate. The PDF's link, filename, and surrounding text enter the verification layer before anything is queued.

Existing PDF changes at the same URL

The easiest case to miss: if a PDF is replaced without its URL changing, a check that only looks at links would see nothing different. Detection also has to compare file size or a content hash, not just the URL.

Surrounding HTML changes

Compared against the last known version of the page's relevant section. Cosmetic changes — styling, unrelated banners — are filtered out; only meaningful content changes proceed to verification.

An old notification is removed

Never treated as notification-worthy on its own. Trackly reports what's newly official, not what disappeared — a removed link usually means reorganization, not a retraction.

Still entirely config-driven — new entries in the same JSON structure. Scheduling likely needs to stagger checks across the day, and a few sites may need bespoke parsing logic for unusual page structures.

Where free-tier limits start to bind

The frontend architecture doesn't change, but reliable change history, per-source scheduling, and failure monitoring at this scale likely need a small persistent backend — even a free-tier one — rather than pure scheduled scripts.

Where Free-First Ends

What will eventually require a real backend

Free-tier schedulers can run a check. They can't, on their own, remember state, manage users, or deliver a notification. Those needs mark the actual boundary of the free-first approach:

  • User accounts and authentication — to know who to notify, and for what.
  • A database — to store subscriptions, the last known snapshot of each monitored page (for comparison), and notification history.
  • Task queue and worker orchestration — once scheduling needs to run reliably across dozens or hundreds of sources instead of a handful.
  • Notification delivery infrastructure — an email sending service, browser push service, and any Telegram/WhatsApp API integration.

Frequently Asked Questions

Common questions about the free automation strategy

Is any of this free automation strategy implemented yet?

No. This page is architecture and planning only — nothing on it is running.

Why not just pay for a server from day one?

Trackly's Version 1 philosophy is free-first: prove the product works before taking on hosting costs. A static site plus scheduled free-tier jobs can genuinely handle five institutes today.

Is GitHub Actions really free forever?

For public repositories, yes — GitHub's hosted runners are free and unmetered on public repos. Private repositories get a monthly minute allowance instead.

What happens if GitHub disables a scheduled workflow?

GitHub automatically disables scheduled workflows after 60 days without repository activity. Any real deployment needs a way to notice and re-enable this.

Is Cloudflare Cron Triggers free?

The trigger itself carries no separate charge, but each invocation counts against the Workers Free plan's 100,000 requests/day and 10ms CPU-time limit, and the free plan allows only 5 cron triggers per account.

Do Cloudflare Cron Triggers retry if they fail?

No. A failed scheduled run isn't retried automatically — the next attempt happens at the next scheduled time.

Why not use RSS for everything?

Because none of ICAI, ICSI, UPSC, SSC, or IBPS currently publish a public RSS feed for their official notifications, as far as this research could confirm.

How will a PDF change be detected if its URL doesn't change?

By comparing the file's size or a content hash, not just checking whether the link still exists — a same-URL replacement would otherwise be missed entirely.

Will a removed notification link ever trigger an alert?

No. Trackly only reports newly official information. A link disappearing usually just means the page was reorganized, not that anything was retracted.

What happens when Trackly needs to support 100 institutes?

The frontend architecture — config-driven pages, reusable components — stays the same. Reliable scheduling, change history, and failure monitoring at that scale will likely need a small persistent backend instead of pure scheduled scripts.

Does this page describe a guaranteed roadmap?

No. It describes a technically realistic strategy given free-tier constraints. The actual implementation may still change once real usage is observed.

Will monitoring ever cost users money?

Tracking itself is free in Version 1. Nothing about this automation strategy changes that.
