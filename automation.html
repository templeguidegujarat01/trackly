Automation Architecture

How Trackly Will Actually Watch Official Sources

This page explains the complete monitoring pipeline Trackly is building toward — how official sources will be checked, how real changes will be verified, and how notifications will eventually reach you. None of this is live yet; this is the architecture, not the product.

Why Automation

Checking five websites by hand is exactly the problem

"Checking automatically" isn't one feature — it's a small pipeline. Something has to decide when to check, fetch the page, notice what changed, confirm the change is real, and only then tell you. This page walks through each piece of that pipeline honestly, including the parts that don't exist yet.

Monitoring Flow

The full pipeline, end to end

  1. Official Website — the institute's real, official page.
  2. Scheduler — decides when to check next. Part of the future automation engine.
  3. Content Check — fetches the current page content. Part of the future automation engine.
  4. Change Detection — compares it to the last known version. Part of the future automation engine.
  5. Verification — confirms the change is real and official. Part of the future automation engine.
  6. Notification Queue — holds the update, ready to send. Part of the future automation engine.
  7. User — gets notified the moment it's official.

Monitoring Methods

How a change could actually be noticed

RSS Feeds

Advantage: Lightweight, standardized, and easy to poll on a schedule without fetching a whole page.

Limitation: Most official Indian government and institute sites don't publish an RSS feed, so this method has limited coverage for the institutes Trackly supports today.

Official Notification Pages

Advantage: Directly authoritative — it's the institute's own listing of its own announcements.

Limitation: Page structure can change without notice, so parsing logic built for one layout can break and needs maintenance.

Sitemaps

Advantage: A standardized file that can reveal new or updated URLs efficiently, without scanning a whole site.

Limitation: A sitemap shows that a page changed, not what changed on it — and not every official site keeps its sitemap accurate or current.

Page Comparison

Advantage: Works even when no feed, sitemap, or API exists — it just needs the page itself.

Limitation: Sensitive to irrelevant changes (ads, timestamps, view counters), so it needs careful scoping to the relevant part of a page to avoid false positives.

Future APIs

Advantage: The most reliable and efficient option, if it ever exists — structured data with no parsing guesswork.

Limitation: None of ICAI, ICSI, UPSC, SSC, or IBPS currently offer a public API for this purpose. This row is aspirational, not a current plan.

GitHub Actions

Scheduled workflows (cron syntax) that can run a check script on a timer, inside GitHub's own infrastructure, within its free usage limits.

Cloudflare Cron Triggers

Cloudflare Workers support scheduled triggers that run a serverless function on a cron schedule — a natural fit for a site already compatible with Cloudflare Pages.

External Cron

A traditional cron job on a server, or a third-party scheduling service that pings an endpoint on a timer. The simplest option, and the easiest to move away from later.

Verification Layer

Why Trackly never trusts random news

A news article can be first, fast, and still wrong. Trackly's verification layer exists so that speed never comes at the cost of accuracy:

  • Only the institute's own official page counts as a source of truth.
  • News articles, social posts, and aggregator sites never trigger a notification, no matter how reliable they usually are.
  • A detected change only becomes a notification after verification confirms it came from the official source itself.

Frequently Asked Questions

Common questions about the automation architecture

Is Trackly already monitoring official websites?

No. This page describes the architecture Trackly is building toward — monitoring isn't live yet.

How will Trackly check for updates without an official API?

By combining official notification pages, sitemaps where available, and direct page comparison — the same general approach a careful human checker would use, just automated.

Will Trackly ever use unofficial sources like news sites or social media?

No. Only the institute's own official page can trigger a notification, regardless of how reliable a third-party source seems.

What happens if an official website changes its page structure?

Monitoring for that source may temporarily need updating. Trackly is built to fail safely — it won't report a fake update just because a page layout changed.

How often will official sources be checked?

That depends on the final scheduler configuration, and will likely vary by institute and update type. No exact frequency exists yet — this page won't promise one before it's actually built.

What is a "false positive" here, and how does Trackly avoid it?

A false positive is a detected "change" that isn't a real official update — for example, a timestamp or ad refreshing. The verification layer exists specifically to filter these out before anything reaches the notification queue.

Will notifications go out immediately after a change is detected?

No. A detected change enters the notification queue only after verification confirms it's a genuine official update.

Which notification channels will be supported first?

That decision hasn't been made yet. Email is the most likely starting point, but nothing is finalized.

Is any of this automation running right now?

No. Everything on this page — scheduler, content check, change detection, verification, notification queue — is architecture, not a live system.

Will Trackly ever charge for automated tracking?

Tracking is free in Version 1. Pricing for any future advanced automation hasn't been decided.
