Data Architecture & Backend Contract

The Data Shape Every Future Piece of Trackly Will Share

This page defines the JSON structures the frontend, the future automation engine, and a future backend would all agree on. Institute and Tracker objects are real — they're what's already running the site. Everything else is a proposed contract, not a running system.

System Data Flow

How data would move through the whole system

Two of these six things are real today. The rest are the proposed pipeline.

  1. Config Files — institutes.json + trackers.json — real, live today
  2. Monitoring Job — A scheduled check for one institute + tracker pair
  3. Change Record — What a job found, before it's trusted
  4. Future Notification — A verified change, ready to deliver
  5. Future API — Would serve these objects as JSON
  6. Frontend Display — Renders whatever the data says — same pattern as track.js

How a scheduled check would be represented

One job per institute + tracker pair, created from the config above. The method field would match the monitoring methods already documented on the Automation Architecture page.

Change Record Structure

Proposed

What a monitoring job produces

A change record is a claim, not a fact yet — verified stays false until the verification layer confirms it.

{ "changeId": "chg_8f2a1c", "jobId": "icai-results-2026-07-30T06:00:00Z", "instituteId": "icai", "trackerId": "results", "detectedAt": "2026-07-30T06:03:12Z", "diffSummary": "New PDF link added: 'CA Final Result - July 2026'", "contentHash": "sha256:9f2c...", "verified": false, "verifiedAt": null }

Monitoring Object Relationship

How every object connects together

Institute and Tracker are the two real, existing records everything else is built from.

  1. Institute — One record per supported institute — real today
  2. Tracker — One record per update type — real today
  3. Monitoring Job — Created for one institute + tracker pair
  4. Change Record — Produced by a job, unverified by default
  5. Future Notification — Produced only from a verified change record

Future Notification Object

Proposed

What a delivered update would look like

Produced only from a verified change record — never created directly, and never skipping verification.

{ "notificationId": "ntf_4c19", "changeId": "chg_8f2a1c", "instituteId": "icai", "trackerId": "results", "title": "ICAI Results Released", "channel": "email", "status": "queued", "queuedAt": "2026-07-30T06:04:00Z", "sentAt": null }

Future API

What a request/response cycle would look like

No such endpoint exists today. This is a contract, not an announcement.

  1. Frontend Request — e.g. GET /api/trackers/icai/results
  2. API Endpoint — Resolves the request — not built yet
  3. Future Database — Looks up the stored objects
  4. API Response — Returns JSON in the shape shown above
  5. Frontend Renders — No rendering logic would need to change

A response would round-trip back up through the same steps, in reverse.

Example response shape

A hypothetical GET /api/trackers/icai/results might return:

{ "institute": { "id": "icai", "name": "ICAI" }, "tracker": { "id": "results", "label": "Results" }, "status": "pending", "lastChecked": null, "lastChange": null }

Future Database Mapping

How these objects would map to storage — concept only

Deliberately technology-agnostic — this works whether storage ends up relational or document-based.

Conceptual database mapping for each object type
Table / Collection Shape Key Relationships
institutes One row per institute id (primary key)
trackers One row per tracker type id (primary key)
monitoring_jobs One row per scheduled check instituteId + trackerId (foreign keys)
change_records One row per detected change jobId (foreign key)
notifications One row per queued/sent notification changeId (foreign key)
subscriptions One row per user's tracked item userId + instituteId + trackerId (foreign keys)

Error Handling Philosophy

Failing honestly, at every layer

The same principle that shaped track.html's error state applies to the data layer itself:

  • A monitoring job that fails to fetch a page is marked failed with a reason — never silently recorded as "no change found."
  • A change record that can't be verified stays unverified. It never auto-promotes into a notification just because time has passed.
  • If a future API can't resolve a request — an unknown institute or tracker — it returns a clear, structured error, not a fabricated empty success. This is exactly what track.js already does today when a URL's org or tracker doesn't resolve.
  • Malformed or missing config data should cause a visible, obvious failure at load time, not a silently broken page that looks fine until someone clicks something.

Versioning Strategy

How this contract can change without breaking anything

  • Config files are additive-first: new fields get added over time, existing fields are rarely removed, so older rendering code keeps working without modification.
  • A breaking schema change would introduce a schemaVersion field on the affected object type, rather than silently changing shape underneath existing consumers.
  • A future API would version its URL path (e.g. /api/v1/...), so a breaking v2 change can't silently break a frontend that was built against v1.
  • This isn't theoretical — Phase 5 already reconciled trackers.json's ids with what the institute pages actually used, and did it without breaking any page that depended on the old file.

Frequently Asked Questions

Common questions about this data architecture

Is any of this data architecture implemented as a real backend?

No. The Institute and Tracker objects are real — they're the actual JSON files powering the site today. Everything else on this page is a proposed structure for future phases.

Why show JSON examples if there's no backend?

So a future backend can be built to match a structure the frontend already expects, instead of the frontend needing to change later.

Are the Institute and Tracker schemas final?

They're what's live today. Fields may be added over time, but Trackly's versioning approach favors adding fields over removing them, to avoid breaking pages that already work.

What happens to a monitoring job that fails?

It should be marked failed with a reason, never silently treated as "no change found."

Can a change record ever skip verification?

No. An unverified change record never becomes a notification, by design.

Will the future API be a REST API?

Not decided. The examples on this page describe a response shape, not a committed technology or protocol.

Does a user subscription object require login?

Yes, conceptually — a subscription belongs to a user, and Trackly doesn't have accounts yet, so this object is entirely aspirational.

Why include a database mapping without choosing a database?

Because the relationships between objects matter more than the specific database technology, and that choice can be made later without changing this contract.

What happens if the frontend requests something the API doesn't recognize?

It should get a clear, structured error — the same honest "not found" handling track.html already does today when a URL has an invalid institute or tracker.

Could institutes.json and trackers.json change in a breaking way?

They could, but the versioning strategy on this page is designed to avoid that — additive changes first, with a documented migration note for anything else.

Is any of this page's content copied from a real, running system?

The Institute and Tracker examples are copied from Trackly's actual data files. Everything marked "future" is a proposed design, not a running system.

Why does this matter before a backend even exists?

Because agreeing on the data shape now means the frontend, automation engine, and backend can all be built independently later without renegotiating how they talk to each other.
